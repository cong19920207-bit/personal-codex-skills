# 对照权威契约的变更门禁

契约是角色，不是文件名：对**本次改动**有约束力的预期行为来源。可以是一份 md、一套目录、被项目声明的 OpenAPI/proto/错误码表，或规则文件点名的路径。

仅在用户显式调用 `$contract-change-review`、点名本 skill、或要求「对照契约/contract 复查」时使用。本 skill **只读**：不改代码、不改契约。不要把它当成通用 code review。

## 1. 定审查范围

优先级：用户本轮指定的文件/模块 → git 未提交或相对基线的 diff → 对话中刚完成的改动。范围不清则先问一句，不扩成全仓审查。

## 2. 定权威源（声明集合，不是命中即停）

先收齐**已声明**的权威源，再决定是否扫描：

1. 用户本轮 `@` / 点名的路径
2. 项目自己点名的来源：`AGENTS.md`、项目规则、`INDEX.md`、`*manifest.json` 中的契约 / contract / API spec 指向

权威源可以是**有序集合**：主源约束行为；被主源引用的 OpenAPI、错误码表等只作补充，**补充不得覆盖主源**。更具体且与本次范围重合的来源优先于总册；冲突只列出，不静默合并。

仅当一个已声明源都没有时，才做**窄扫描**：排除下文「默认不是契约」的路径后，只收高信号文件（文件名或入口明确为 spec / contract / openapi / proto 等）。扫描结果在报告中列出「未纳入的候选」。不得把未声明文件升格为与主源并列。

- **≥2 个已声明源且可能打架**：问一次（列出路径与各约束什么）
- **零候选**：不问「选哪个契约」，按「无契约」降级

每次报告开头写：

```text
权威契约：<路径或「未找到」>
审查范围：<diff / 文件 / 模块>
```

无契约时追加：`已降级：1/2/7 无对照，3–6 N/A`。

### 默认不是契约

除非用户或项目规则点名，下列不当权威源：README、changelog、会议纪要、PRD 全文、代码注释、测试用例；以及 `node_modules`、vendor、dist、generated、archive、history、snapshot、draft。

测试默认是**实现证据**，不是权威源。PRD 默认走需求审查，不自动当 contract。不读 `.env`、密钥及其内容。

若项目存在 `contract-manifest.json` 或等价入口且已被声明，按其读序**只读与本次改动相关**的模块；这是加速，不是默认布局。

### 无契约时的降级

- 检查项 1 / 2 / 7：记「未找到契约」或 N/A，不得编造条款
- 检查项 3–6：**N/A**（无对照条款）。diff 里若已看见崩溃级问题，最多一两句提及，不展开缺陷清单
- 用户要的是通用 code review：不在本 skill 补全套审查

## 3. 拆条对照（打分前必须做）

从 diff 抽出符号：路由、字段、错误码、权限、事件、表/消息名。用这些符号回搜权威源，只把**命中条款**进表。命中很多则按资源/接口分组，不 dump 全文。权威源中完全没碰到的章节视为**本次未覆盖**，不判 ❌。

无条款 ID 时用「文件 + 标题/段落」定位。按**条款**标注「应当怎样」或「当前是什么」，不要给整份文件打一个类型标签。两种并存且冲突时拆开写。

```text
条款 | 来源位置 | 应当怎样 / 当前是什么 | 实现证据 | 结论（一致/部分/缺失/偏离/本次未覆盖）
```

7 项是这张表的汇总，不是另一套空泛 checklist。

## 4. 七项门禁（按顺序）

对每一项独立给 ✅、❌ 或 N/A。禁止用模糊表述代替结论。每项下可有 N 条发现；该项 ✅ 当且仅当 0 条 ❌。

第 3–6 项只审：权威源有对照条款，**且**由本次改动引入或触及。无对照条款则该项 N/A。

| 序号 | 检查项 | 要点 |
|------|--------|------|
| 1 | 契约对齐 | 权威源中实际存在的需求点、接口、数据模型、错误码、权限等，是否在实现中有对应且一致 |
| 2 | 功能完整性 | 权威源中的功能点是否均已实现；有无只做一半或占位未接逻辑 |
| 3 | 其他缺陷 | 崩溃、空指针、并发、资源泄漏、错误处理缺失等明显 bug |
| 4 | 冲突与兼容性 | 与现有功能、对内/对外 API、迁移、缓存键、事件名等是否冲突或破坏兼容 |
| 5 | 边界与异常 | 空输入、极大/极小值、超时、重试、幂等、空列表、权限不足等 |
| 6 | 规范一致性 | 仅当权威源或本仓 `AGENTS.md`/README **写明了**命名、分层、错误处理、日志等时才查；否则 N/A 通过 |
| 7 | 权威契约是否同步 | 实现偏离或扩展后，权威源是否已更新；版本/变更说明是否需补充 |

## 5. 输出格式（必须遵守）

项级三种：

```text
✅ 通过 — [一句话依据：对照了哪类条款、哪段代码]
N/A — [无对照条款 / 未找到契约 / 规范未写明]
```

❌ 下可多条，每条：

```text
❌ 问题 — [文件路径、函数/接口名、行号或模块]
错误内容：[客观描述]
修复建议：[可执行方向]
风险等级：高 / 中 / 低
是否必须修改：是 / 否（否时写可接受条件或后续跟进）
错误类型：[功能遗漏 / 逻辑缺陷 / 接口冲突 / 边界处理不足 / 规范不一致 / 文档未同步 / 其他]
```

缺证据时用 **待验证**（写清缺什么），**不计入 ❌、不充当否决**。

### 文末汇总（勿省略）

```text
必须修：X
待验证：Y
建议项：Z
门禁：通过 / 不通过
```

仅 `必须修 = 0` 写「门禁通过」。否则写「门禁不通过（必须修 X）」。待验证与建议项另列。

## 执行原则

- **证据优先**：结论可追溯到代码路径、接口定义或权威源条款。
- **最小臆测**：不编造权威源中不存在的条款；实现与契约冲突时写明冲突点。
- **范围聚焦**：只评本次改动与直接依赖，避免无关文件的泛泛评论。

## 与其他技能

本 skill 单独能跑。若用户还装着下列技能，可提示更合适的入口（没装则忽略）：改前分析 → `pre-change-analysis`；需求未拍板 → `requirement-integrate-and-confirm`；三方大审查 → `tripartite-execution-review`；从代码建契约 → `contract-from-code`。

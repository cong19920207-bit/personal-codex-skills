# 三方交叉：需求 + 现有代码 + 新方案审查

## 何时使用

用户要求对 **执行方案/新代码** 做全面审查，且需要同时对照 **需求文档** 与 **已上线（或当前基线）代码** 时，按本技能执行。若用户未显式粘贴三块内容，先从对话与 `@` 引用中补齐；仍缺失则列出「待补充」项并基于已有材料继续审查，**不得虚构**需求或线上事实。

## 角色与立场

以资深代码审查专家与系统架构师身份输出：结论明确、可执行，区分事实与推断；推断处标注「推断」及依据。

## 用户输入模板（可提示用户按此提供）

若信息不全，可请用户按下述结构粘贴或引用文件：

```text
【需求文档】
{需求全文或核心要点}

【已上线的现有代码】
{相关模块/接口/表结构等}

【待审查的新方案/代码】
{AI 生成的方案或 diff/片段}
```

## 审查流程

1. **建立对照表**：从需求中抽出功能点、验收标准、非功能约束；从现有代码中抽出对外契约（API、事件、表结构、配置键等）；再映射到新方案中的对应实现。
2. **优先级**：先完成 **维度 0（需求对齐）** 与 **维度 1（与现有代码兼容）**，再展开其余维度。
3. **逐维审查**：每个发现的问题必须输出下列三项（无问题时该维度可写「未发现明显问题」并简述依据）：
   - ① **问题描述**（含与需求/旧代码/新方案的对应关系）
   - ② **风险等级**：高 / 中 / 低
   - ③ **具体修改建议**（可含伪代码、接口形状、迁移步骤要点）

## 审查维度（按变更适用性选择）

需求对齐与基线兼容是三方对照的核心。其余维度仅在改动、验收或风险涉及时检查；不适用项可集中说明，不制造空问题。只读取所选维度需要的来源；已有证据前提未变时复用。同一问题分配一个稳定编号，涉及多个维度时引用该编号，不重复审查或列项。

### 0. 需求对齐检查【优先级最高】

- 新方案是否完整覆盖需求中所有功能点；有无遗漏、误解或过度实现。
- 实现方式是否符合需求原始意图；验收标准是否可验证、可满足。

### 1. 与现有代码的兼容性【优先级最高】

- 命名、接口格式、模块边界是否与线上/基线冲突。
- 数据结构或库表是否破坏性变更；入参/出参/状态码契约是否一致。
- 是否需要数据迁移及安全性；回归风险与影响面。

### 2. 逻辑正确性

- 核心逻辑漏洞、边界条件；算法能否达成目标；死循环、无限递归等风险。

### 3. 异常与错误处理

- 异常场景覆盖度；错误信息可排查性；回滚/降级；与现有错误规范一致性。

### 4. 执行顺序与依赖关系

- 步骤顺序与隐性依赖；并发/异步下的竞态。

### 5. 安全性

- 注入类风险；敏感数据处理；权限与现有权限体系对齐。

### 6. 性能与资源

- 瓶颈、资源释放；大数据量/超时；对现有服务的影响。

### 7. 兼容性与环境依赖

- 环境假设；第三方依赖冲突；跨平台问题。

### 8. 上线部署风险

- 平滑上线 vs 停机；配置/环境变量；部署顺序；回滚方案。

### 9. 可维护性与完整性

- 方案是否缺步骤；风格一致性；日志、注释、监控是否足够。

## 汇总报告

先给审查结论，再按风险列出阻断问题、非阻断建议及其证据和最小修改建议，说明未核实范围与下一步。同一发现只保留一处完整描述；需求偏差和代码冲突用标签或问题编号关联。无问题时简述范围和验证依据，不输出空表。评分、正向点评和固定展示结构只在用户要求时提供。

## 输出约定

- 使用简体中文；术语与代码标识保持原文大小写。
- 需求对齐与兼容性中的高风险项应优先报告；只对本次已核实范围给出结论。
- 本技能默认只审查；后续修改或敏感操作须遵守相应授权，不把审查请求当作实施许可。

## 与其他技能的关系

- 契约按项目声明的权威角色定位，不固定文件名。需要补足专门能力且满足对应技能触发条件时才调用；已有相关审查或根因分析直接引用有效结论，不叠加同职责全流程。

# PRD From Chat

## 核心原则

把当前对话和用户提供的材料整理为可追踪、可验收的 PRD。更新时，现有 PRD 是基线，后续对话和新材料是增量。只把有来源的内容写成已确认需求；不得把 AI 归纳或建议伪装成用户决策。

## 手动触发边界

- 仅在用户显式调用 `$prd-from-chat` 时执行。
- 未显式调用时，不主动建议生成或更新 PRD。
- 上传文件、出现功能决策或用户说“确认”都不能单独触发本 Skill。

## 按模式读取参考

先识别模式，再加载必要参考：

- 首次生成或结构重整：读取 [references/prd-template.md](references/prd-template.md) 的基础结构和适用扩展；不加载不适用的扩展。
- 增量/局部更新：以现有 PRD 为基线，仅在新增结构需要时查模板相应部分。
- 生成、更新、回滚或审查：使用 [references/review-checklist.md](references/review-checklist.md) 的适用检查；首次生成、整体重整和明确要求全面审查时覆盖完整适用范围，局部修改检查变更及必要依赖。
- 原样导出：只读取目标原文并校验输出一致性，不加载创作模板或完整审查清单。

未变化且仍适用的已读参考和验证结果可复用；最终修改内容必须在交付前核对。

## 模式识别

| 模式 | 用户意图 | 默认行为 |
|---|---|---|
| 首次生成 | 从聊天或材料生成 PRD | 生成 `v1` |
| 增量更新 | 把新讨论加入已有 PRD | 生成 `vN+1`，保留旧版本 |
| 局部更新 | 只修改指定章节 | 同步更新必要的引用、版本和版本记录 |
| 审查 | 检查遗漏、冲突或幻觉 | 默认只报告，不改文件 |
| 导出 | 查看或重新输出已有 PRD | 复制原文，不擅自重写 |
| 回滚 | 恢复历史版本内容 | 必须读取真实历史文件，并生成新的前向版本 |

如果意图不明确，优先根据用户动词和是否提供现有 PRD 判断；只有不同模式会产生实质不同结果时才追问。

## 来源解析

### 更新基线

按以下顺序定位现有 PRD：

1. 用户本轮明确提供或指定的文件、附件或路径。
2. 当前对话中最近一次由本 Skill 生成且仍可访问的唯一 PRD。
3. 当前可访问范围内唯一、名称与项目明确匹配的 PRD。

更新、局部更新或回滚时，如果不能唯一定位基线，停止写入并只询问用户提供目标文件。不要使用未定义的状态别名、跨任务记忆或未验证的路径代替真实文件。

### 需求来源优先级

发生冲突时按以下优先级处理：

1. 用户最新且明确的替换、取消或确认指令。
2. 用户明确标记为已批准的材料。
3. 现有 PRD 中的当前有效要求。
4. 更早的对话和普通参考材料。
5. AI 归纳与建议。

最新内容明确表达“改为、替换、不再、取消”时，更新当前要求并把旧决策标记为已废止。只是表述不同、指代不清或可能同时成立时，展示冲突并等待用户决策。

### 内容状态

| 状态 | 使用条件 |
|---|---|
| ✅ 已确认 | 用户明确确认，或来自明确批准的材料 |
| ⚠️ 待确认 | 信息缺失、表述模糊或 AI 根据上下文归纳 |
| 💡 AI 建议 | AI 提出的产品或技术建议，不属于当前要求 |
| ⛔ 已废止 | 被后续明确决策替换；保留追踪关系但不再执行 |

来源使用当前环境真实可定位的信息，例如“本轮对话”“需求说明.md §3”“`src/api.ts`”。没有稳定消息编号时不虚构编号。决策编号和需求编号一旦发布不得复用；反向决策新建编号并记录其替代关系。

## 信息不足

仅在以下情况补问：

- 首次生成时无法判断要解决的问题或需求对象。
- 更新、局部更新或回滚时无法定位唯一基线。
- 新旧内容存在会改变范围或实现结果的真实冲突，且用户没有明确替换关系。
- 写入将覆盖已有文件，但用户没有明确授权。

每轮最多问两个阻塞问题。非阻塞缺口使用 `⚠️ 待确认`，继续生成可评审版本。验收标准属于核心内容；无法确定时必须标为待确认，不能编造阈值。

## 执行流程

### 首次生成

1. 汇总当前可见对话和用户材料，区分已确认、待确认、AI 建议和已废止内容。
2. 使用模板生成基础 PRD；只在适用条件成立时加入 AI/Agent 或技术实施扩展。
3. 使用统一整数修订号 `v1`，确保文档头和文件名一致。
4. 执行审查清单，先修复可修复的问题，再交付文件。
5. 使用当前运行环境可用的文件工具和用户输出目录；不硬编码工具名或路径。

用户显式要求生成文件已经构成写出授权。没有阻塞问题时，不强制先在对话中粘贴全文并等待二次确认。

### 增量更新

1. 读取并解析基线 PRD，包括当前版本、有效决策、待确认项和版本记录。
2. 将当前可见的新对话和材料与基线逐项比较，分类为新增、修改、废止、补充或重复。
3. 没有实质变化时不创建空版本，直接说明未发现需要写入的增量。
4. 保持未受影响内容不变；只修改相关章节以及必要的交叉引用。
5. 默认使用下一整数修订号 `vN+1`：`v1 → v2 → v3`。
6. 默认保留旧版本。源目录可写时，在同目录生成下一版本文件；不可写时，输出到宿主规定的用户交付目录并说明原文件未改变。
7. 只有用户明确要求覆盖时才原地覆盖，并先说明覆盖会失去精确历史回滚能力。
8. 在版本记录顶部新增一行，列出新增、修改、废止和仍待确认内容。
9. 对变更及受影响的决策、引用和验收项合并执行一次审查，并比较基线排除无关漂移；跨章节重整或新证据表明影响扩大时扩大检查。交付精简 diff 和剩余不确定性。

现有文件没有可解析版本时，将它视为未版本化基线，下一份保存为 `v1`，不得擅自改写原文件。

### 局部更新

只修改用户指定章节，以及为保持一致性必须同步的文档头、引用、验收项和版本记录。审查时比较基线，确认其他章节没有无关漂移。

### 审查与修复

- 用户只要求“审查”时，按指定范围执行清单并报告问题，不写文件；未限定范围的整体审查覆盖全部适用项。
- 用户要求“审查并修复”时，以修复后的内容生成下一版本，不覆盖原文件。
- 无法验证的技术信息降级为待确认或“未检查代码”，不得用更流畅的措辞掩盖证据缺口。

### 导出

重新输出可访问的现有文件，不重写内容。用户要求改变格式、合并材料或修正文档时，切换到更新模式并产生下一版本。

### 回滚

回滚必须读取真实历史文件。若当前为 `v4`，用户要求恢复 `v1` 内容，则基于真实 `v1` 生成 `v5`，并记录“回滚到 v1 内容”；保留 `v2` 至 `v4`。如果历史正文不可用，明确说明无法精确回滚，不得根据版本摘要重新生成。用户只要求重新导出旧版时，原样导出该历史文件，不创建新版本。

## 技术信息边界

技术实施方案可以进入 PRD，但必须满足至少一个条件：

- 用户提供了明确技术方案或接口资料。
- 用户授权并提供了可检查的代码仓库、配置或数据结构。
- 内容明确标记为 `💡 AI 建议`，没有冒充既有实现。

只有实际检查过代码后才能断言文件路径、函数、接口、字段和改动范围。未检查时写“未检查代码仓库”或省略不适用章节。

## 文件与版本规则

- 默认文件名：`PRD-[项目名]-vN.md`。
- 文档头、文件名和版本记录必须使用同一版本。
- 项目名清理宿主不支持的路径字符；不得因清理后重名而覆盖文件。
- 版本记录按新到旧排列。
- 用户已有明确版本方案时沿用，但不得产生倒退版本或文件名冲突。
- Skill 不维护隐式全局状态；真实文件始终是版本事实来源。

## 交付格式

文件交付后只需说明：

- 生成或更新的版本及文件位置。
- 本次新增、修改、废止的摘要。
- 审查结论、已修复问题和仍待确认项。
- 是否检查过代码或其他技术证据。

不要宣称“零幻觉”或“绝对无遗漏”。使用“本轮审查未发现无来源的确定性断言”等可验证措辞，并明确残余不确定性。除非用户要求，不在对话中重复粘贴完整 PRD。

## 常见错误

- 把普通肯定词错误绑定为需求确认。
- 把 AI 建议写成已确认决策。
- 为填满模板而猜测用户、指标、文件、接口或数据结构。
- 只改版本号，没有将对话增量落实到流程、边界和验收。
- 更新时重写无关章节，造成语义漂移。
- 在没有历史正文时声称已经回滚。
- 审查发现问题后仍交付未修正版本，却没有说明残余风险。

# PRD 交付前审查清单

## 审查原则

生成、修改、回滚或审查 PRD 时使用本清单的适用项。首次生成、整体重整和全面审查覆盖完整适用范围；增量/局部修改只检查变更及受影响的决策、引用和验收，并对比基线排除无关漂移。原样导出只校验源文件与输出一致，不执行创作审查。

合并重复检查；已验证且输入和前提未变的结果可复用。审查后修复时只复核修复及其影响。模型不能证明“没有幻觉”，只能检查无来源的确定性断言并披露未验证内容。

## 审查流程

1. 列出本次真实输入：对话范围、附件、基线 PRD、代码或技术资料。
2. 对照输入逐项审查草稿，不把草稿本身当作证据。
3. 已授权修复时处理遗漏、错误引用、冲突、版本问题和非必要改写；只读审查只报告问题和建议，不修改原文。
4. 无法从来源确认的内容改为 `⚠️ 待确认`、`💡 AI 建议` 或删除。
5. 再检查修复后的文档，给出 `通过`、`通过但有待确认` 或 `阻塞`。

## 1. 来源忠实度与幻觉检查

- 每个已确认需求、决策、数字、阈值和限制都能对应到真实来源。
- 文件路径、函数、接口、字段、架构和现有系统行为只在实际检查后写成事实。
- 对话中的“对”“确认”等短答复绑定到了明确的被确认对象。
- AI 归纳使用 `⚠️ 待确认`，AI 提案使用 `💡 AI 建议`。
- 没有伪造消息编号、文件章节、代码位置、负责人、日期或测试结果。
- 没有用行业惯例补齐用户未决定的业务规则。

发现无来源断言时，先删除、降级或补充来源。最终只能报告“本轮审查未发现无来源的确定性断言”，不得写“零幻觉”。

## 2. 遗漏与完整性检查

- 背景、问题、目标、用户场景、范围、非目标、功能流程、边界和验收均已评估。
- 每个核心需求至少有一个关联验收项，或明确标记验收待确认。
- 关键名词、角色、状态和对象前后一致。
- 适用的依赖、风险和待确认项没有被埋在正文中。
- 涉及 AI/Agent 时，已评估背景与目标、能力边界、Agent 行为、Prompt / 指令、知识与数据、工具与接口、异常与降级、评估与验收。
- 涉及技术实施时，已评估架构、数据、接口、代码影响、迁移发布、可观测性、安全隐私和技术债；不适用或未检查的内容已明确说明。

不要为了“完整”创建无意义的空章节。完整性是适用项均被评估，不是模板标题越多越好。

## 3. 决策与逻辑一致性检查

- 同一问题只有一个当前有效结论；旧结论已标记 `⛔ 已废止` 并指向替代编号。
- 决策编号、需求编号和验收编号唯一且未复用。
- 范围、主流程、异常处理、数据规则和验收标准互相兼容。
- “明确不做”的内容没有出现在当前需求或验收中。
- 状态、角色、权限、时序、默认值和优先级没有跨章节冲突。
- 新版本的变更摘要与正文实际变化一致。

## 4. 可测试性检查

- 验收标准描述可观察输入、事件和预期结果，避免“体验良好”“尽量快”等不可判定表达。
- 边界、错误和降级路径包含预期系统行为与用户反馈。
- 指标、门槛和样本范围有来源；未确定的阈值明确标记待确认。
- AI/Agent 评估说明数据集或场景、方法、版本和上线门槛。
- 技术要求包含必要的兼容、权限、幂等、超时、重试或回滚验证。

## 5. 更新保真检查

- 本轮新增、修改、废止、补充和重复内容已正确分类。
- 未受影响章节没有被无关重写、删减或改变含义。
- 最新明确决策已生效，模糊冲突没有被擅自裁决。
- 局部更新只触及目标章节以及必要的头部、引用、验收和版本记录。
- 没有实质增量时没有创建空版本。

## 6. 版本完整性检查

- 文档头、文件名和版本记录使用同一版本。
- 新版本是基线的下一整数修订号，或遵循用户已有且无冲突的版本方案。
- 版本记录按新到旧排列，准确描述本轮变化和待确认项。
- 默认保存路径不会覆盖旧版本；旧文件仍然存在。
- 回滚使用了真实历史正文，并产生新的前向版本；没有根据摘要伪造历史内容。

## 7. 技术真实性检查

- 技术事实来自用户材料或实际代码、配置、接口、数据结构检查。
- 已验证文件路径和符号确实存在，引用范围与结论匹配。
- 没有把拟议方案写成现状，也没有把现状误写成已批准方案。
- 未访问代码时明确写“未检查代码仓库”，不生成虚构文件索引。
- 安全、隐私、权限、迁移和发布结论没有超出已知证据。

## 阻塞条件

出现以下任一情况时，不写出更新版本：

- 更新、局部更新或回滚缺少唯一、真实的基线文件。
- 核心范围存在互斥决策，且用户最新表达不能明确解决冲突。
- 写入会覆盖已有文件，但用户没有明确授权。
- 用户要求精确回滚，但历史正文不可用。

其他缺口不阻塞生成，统一标记待确认并在交付摘要中列出。

## 审查结果格式

```text
审查结论：[通过 / 通过但有待确认 / 阻塞]
已修复：[遗漏、冲突、无来源断言或版本问题；无则写“无”]
剩余待确认：[编号及影响；无则写“无”]
来源范围：[对话、文件、代码等]
技术证据：[已检查的范围；未检查则明确说明]
```

如果结论为阻塞，只输出阻塞原因和所需的一个关键输入，不声称已完成 PRD 更新。

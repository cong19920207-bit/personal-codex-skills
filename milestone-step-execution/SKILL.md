# 里程碑 STEP 执行

## 手动触发

仅在用户明确要求使用 `$milestone-step-execution`，或已授权上游流程按协议交接规划/闸门时使用。讨论或审查技能本身不算调用。
不要仅因用户提到 PRD、STEP、里程碑、开发批次、阶段验收或契约而自动触发。

## 核心定位

将已经确认的开发 STEP 编排为可验收的 `M1…Mn`，并把确认后的 STEP 或批次交给
`$execute-approved-work` 按顺序实施；全部里程碑通过后，负责正式契约整合及最终
契约验证闸门。

**本 Skill 只负责执行分组、顺序、批次、阶段闸门，以及最终正式契约整合和验证
闸门；不改变需求或 STEP 内容，也不自行建立另一套代码执行粒度。**

## 入口模式

- `standalone`：用户直接调用本 Skill。规划请求只输出本阶段计划；用户已明确授权开发且满足执行门禁时，将当前 STEP 或已确认批次交给 `$execute-approved-work`，本 Skill 保留里程碑推进和闸门判定。完成当前授权范围后结束；内部交接不终止已授权的后续流程。
- `orchestrated`：由 `$prd-delivery-harness` 在 Phase 3 读取本 Skill 后执行，只生成
  `{功能名}开发里程碑文档.md`，不等待重复的阶段确认，不执行 STEP。此模式不含业务代码或正式 Contract 写入；只有用户明确授权相应执行范围后，才能转入执行编排。

`orchestrated` 的唯一 STEP 输入是通过完整复审的 `steps-verified.md`。只有 `steps-draft.md`、`steps-provisional.md`，或存在关键未核实路径/符号时，返回 `FAILED_VALIDATION` 并停止；时间压力、已投入成本和上线承诺不能替代上游门禁。

## 前置条件与模式

必须同时具备：

- 已确认的 PRD 或等价需求文档；
- 已拆解完成、含完成标志或验收口径的开发 STEP；
- 用户提供或可从项目中发现的开发规范。

缺少 STEP 时停止，建议先使用 `prd-to-steps`。STEP 与 PRD 存在无法由有效来源消解的不一致时，报告并暂停受影响项及其依赖；需要审查时建议使用 `step-doc-review`。

根据用户意图区分：

- **规划模式**：用户只要求制定计划、讨论拆分或安排顺序时，按请求输出或保存草案，不执行开发。保存草案不等于批准执行；仅尚未决定的范围和关键取舍需要确认。
- **执行编排模式**：仅用于 `standalone`，且用户已明确授权开发时，按已确认计划选择当前 STEP 或批次，并交给 `$execute-approved-work` 实施、验证和记录；本 Skill 负责接收结果、推进里程碑和判定闸门，不替代 STEP 自身的技术要求。`orchestrated` 禁止进入此模式。

## 来源与阶段结果

来源标签统一为：`USER_DECISION`、`PRD`、`CONTRACT`、`REPO_BASELINE`、`RUNTIME`、`PLANNED`、`UNVERIFIED`。计划引用的现有路径/符号必须有 `REPO_BASELINE` 证据；总控模式中还必须保留上游 `source_id` 与可核实 `locator`，不得把新路径重新标成 existing。新产物标 `PLANNED`；关键 `UNVERIFIED` 不能进入正式执行计划。没有 `RUNTIME` 证据时，不声称线上行为已验证。

| 结果 | 使用条件 |
|---|---|
| `PASS` | 计划覆盖、依赖、批次和验收均通过，风险列表为空 |
| `PASS_WITH_RISKS` | 门禁通过，仅有明确的非阻断风险 |
| `DOCUMENT_ONLY` | 只能讨论暂定分组，不能生成正式的 `{功能名}开发里程碑文档.md` |
| `BLOCKED` | 存在未解决的业务或高风险决策 |
| `FAILED_VALIDATION` | 总控模式输入不是有效 `steps-verified.md`、关键来源未核实、计划遗漏/重复或来源变化后尚未重新核验 |

只要列出非阻断风险就使用 `PASS_WITH_RISKS`。`BLOCKED` 或 `FAILED_VALIDATION` 不得继续。

## 源文档不可改写

将 PRD、补充规格和 STEP 正文视为只读事实来源：

- 不新增、删除、改写或合并需求与 STEP；
- 不改变原有业务语义、范围、完成标志或验收口径；
- 不用实施计划补造 STEP 中不存在的需求；
- 发现影响范围、验收或可行性的遗漏/冲突时暂停受影响项；能由有效来源消解的定位和引用问题直接核验。需要产品或授权决定时向用户提出，独立已授权项继续。

实施计划只能引用 STEP 编号、标题和原验收口径。

## 与执行 Skill 的边界

- 里程碑控制阶段边界，STEP 控制执行边界，验收点控制测试粒度；
- 本 Skill 生成顺序、批次、验收清单和阶段闸门，不把 STEP 重拆为新的开发任务；
- `$execute-approved-work` 默认整体实施当前 STEP，只能按需建立不改变 STEP 的内部
  验证检查点；
- 验证方式是证明原完成标志的手段，不构成新的业务需求；
- `$execute-approved-work` 负责运行验证并提交 `GATE_EVIDENCE_READY`；本 Skill
  独占里程碑闸门判定和下一里程碑推进，不把判定权交给执行器；
- 本 Skill 负责把全部有效临时契约整合进正式契约；整合后由
  `$execute-approved-work` 只做契约一致性和受影响回归验证并提交
  `CONTRACT_VERIFICATION_READY`，本 Skill 独占 `CONTRACT_MERGED_VERIFIED` 的判定权；
- 执行器发现修复需要越过 STEP、共享契约或既定计划边界时，必须返回外溢证据，
  本 Skill 不得静默重排或改写来源以绕过门禁。

## 统一执行工作区

以本次权威 STEP 所在目录作为阶段目录 `{phase_dir}`；总控模式要求有效 `steps-verified.md`，独立模式接受用户确认且证据充分的等价 STEP，不按文件名判定有效性。创建新执行文档前，
先确定 `{功能名}`：

1. 优先采用用户明确确认的功能名；
2. 用户未单独命名时，复用现有名称，否则采用来源文档标题或清晰短名；
3. 只有命名冲突、覆盖风险或对外命名的实质取舍才询问，普通文件名自行确定；
4. 文件名保持人类可读，只清理路径分隔符和当前文件系统不允许的字符。

没有用户明确指定的其他权威路径时，两个 Skill 共用以下工作区：

```text
{phase_dir}/execution/
├── {功能名}开发里程碑文档.md
├── {功能名}开发执行记录.md
├── contract-drafts/
└── evidence/
```

- 本 Skill 生成和维护 `{功能名}开发里程碑文档.md`，并在共享的
  `{功能名}开发执行记录.md` 中更新计划状态、里程碑状态和闸门判定；
- `$execute-approved-work` 在同一份 `{功能名}开发执行记录.md` 中更新 STEP 状态、
  改动、验证证据、阻塞和恢复点，不另建执行日志；
- `contract-drafts/` 仅在存在契约增量时创建，保存 STEP 增量和里程碑临时契约；
- `evidence/` 仅在大型或独立证据文件确有需要时创建；
- 正式契约保持项目原权威路径，不移入过程工作区；
- 执行交接提示不持久化为逐次文件。

例如 `realtimevoice/p1/steps-verified.md` 对应
`realtimevoice/p1/execution/实时语音通话开发里程碑文档.md` 和
`realtimevoice/p1/execution/实时语音通话开发执行记录.md`。

已有活跃实施计划或进度记录位于其他路径或使用旧文件名时，不自动移动、重命名或
复制；继续复用既有权威路径，除非用户明确授权迁移。新阶段和没有既有约定的执行
统一采用上述布局和功能名文件名。

## 先发现项目约定

优先使用用户及上游提供的有效路径和既有记录；缺少当前模式必需位置时再定向查找。按本次范围读取 PRD/STEP、规则和计划；仅涉及契约增量或整合时定位相应契约，不先扫描全套文档。

优先复用已有活跃路径和格式。新阶段缺少执行文档且没有项目专用约定时，直接采用
`{phase_dir}/execution/` 布局；这不等于假设固定的项目 `docs/` 层级。本次确需写正式契约且无法从项目约定确定权威位置时，再提出具体方案确认；无契约变更不询问。

## 自适应划分里程碑

用户指定的阶段和约束优先。用户未指定时，根据以下信息提出 `M1…Mn` 草案：

1. STEP 的显式与隐式依赖；
2. 每组可独立验证的交付能力；
3. 技术风险、外部依赖和回滚难度；
4. 文件、数据、接口和契约冲突；
5. 用户要求的节奏、资源或发布日期。

里程碑数量不固定；简单模块可以只有一个，复杂模块可以有多个。不要机械按 STEP 编号、技术层或固定功能类型分组。

每个里程碑必须定义：

- 名称与一句话目标；
- 包含的 STEP、建议顺序和可并行候选；
- 前置依赖与明确排除项；
- 逐条验收清单和验证方式；
- 有契约增量时的临时契约位置，否则注明“不适用”；
- 进入下一里程碑的闸门。

每个里程碑至少包含一个 STEP；不得用空里程碑占位。

展示划分及依据，将尚未决定的阶段范围、关键取舍和必要授权合并为一次确认。已有决定或授权可覆盖这些内容时直接复用；无新增决策不因保存计划或进入执行再次确认。只授权规划时不得实施代码。

## 决定执行批次

默认一次执行一个 STEP。多个 STEP 仅在同时满足以下条件时才可组成一个批次：

- 不存在未完成的先后依赖；
- 不会产生文件、数据、接口或契约冲突；
- 每个 STEP 可以独立验证、记录和回滚；
- 不跨越里程碑闸门。

批次数量不设固定上限。实施计划写明合批依据和独立验收方式；纳入同一次计划确认，已批准批次不再单独确认。未批准的并行或合批若会改变风险/交付顺序则先决策，否则继续既定顺序。

## 工作流程

### 1. 生成计划草案

1. 读取源文档与项目约定，建立 STEP 依赖关系。
2. 生成 `M1…Mn` 划分、批次建议、风险和验收闸门。
3. 标明所有假设、冲突和待确认项。
4. 仅对尚未决定的范围、关键取舍和执行授权集中确认。

按已获授权的文档输出范围，在统一执行工作区写入 `{功能名}开发里程碑文档.md`，并建立或更新共享的
`{功能名}开发执行记录.md`。首次创建或现有结构不适用时读取
[实施计划模板](references/implementation-plan-template.md)，常规更新沿用现有结构。

在 `orchestrated` 中，总控已授权本阶段规划，跳过上述重复确认并直接生成
`{功能名}开发里程碑文档.md`；计划状态必须是 `IMPLEMENTATION_PLAN_READY`，业务代码
状态必须是 `NOT_STARTED`，随后把阶段结果交回总控并停止。

### 2. 发起 STEP 或批次执行

执行前核对当前里程碑、前置依赖和本批范围，复用未失效的已核实事实。在 `standalone` 中读取并遵循
`$execute-approved-work`，把实施计划、STEP 原文、验收清单、进度记录和项目规范
作为执行输入。开发要求完全引用原 STEP，不重新解释为新需求。

每次交付至少包含：

- STEP 级改动文件列表；
- 对应原完成标志的验证证据；
- 契约增量草稿，或“无契约变化”及依据；
- 阻塞项、风险或偏差。
- 到达里程碑边界时的 `GATE_EVIDENCE_READY` 与闸门证据。

只有原 STEP 的完成标志全部满足时才更新为完成。首次构造交接或字段不明时读取 [执行指令模板](references/execution-prompt-templates.md) 的对应模板，不重复加载其他阶段模板。

### 3. 里程碑验收

本里程碑所有 STEP 完成后：

1. 接收执行器的 `GATE_EVIDENCE_READY`、STEP 验证结果和运行证据；
2. 按已确认验收清单判定；复用前提未变且覆盖当前版本的证据，仅补缺失/失效或计划明确要求重跑的验证，不开发新功能；
3. 证据缺失或未通过时记录缺口并留在当前里程碑；
4. 全部通过后由本 Skill 明确判定闸门通过；
5. 有契约增量时汇总为临时契约文档；无增量则在进度记录中注明依据，不生成空文档；
6. 本 Skill 判定闸门通过且后续工作仍在用户授权内时继续下一里程碑，不为内部交接要求用户再次点名。

首次生成临时契约且无适用项目格式时读取 [临时契约模板](references/contract-draft-template.md)，保存到执行工作区
的 `contract-drafts/`，只记录本里程碑的新增、变更和兼容影响。

### 4. 整合并验证正式契约

仅当所有里程碑均完成并通过业务总验收后执行。有契约增量时走以下整合流程；全范围无契约增量时核对各 STEP 证据，记录契约状态 `NOT_APPLICABLE` 及依据，满足其余完成条件即可结算，不虚构契约写入或 `CONTRACT_MERGED_VERIFIED`：

1. 读取全部里程碑临时契约和项目现有正式契约；
2. 按项目既有结构合并所有有效变更；
3. 更新已有条目而不是创建语义重复项；
4. 检查跨阶段冲突、重复、废弃项和兼容说明；
5. 写入后将契约整合状态记为 `CONTRACT_MERGED_PENDING_VERIFICATION`，保留临时契约
   作为阶段快照，但不得宣布整个功能完成；
6. 把正式契约、全部临时契约、受影响实现位置、计划已有验证要求和共享进度记录
   交给 `$execute-approved-work`；
7. 接收执行器的 `CONTRACT_VERIFICATION_READY`，逐项判定最终契约验证闸门；
8. 全部证据通过后标记 `CONTRACT_MERGED_VERIFIED`，更新实施计划与共享进度记录，
   此时才允许结算整个功能完成；任一项未通过或证据缺失时标记 `BLOCKED`。

整合后验证必须覆盖：

- 每一项有效临时契约增量在正式契约中都有唯一、语义一致的落点，且无遗漏、重复、
  冲突或误废弃；
- 受影响的接口、数据、事件、配置、权限、枚举或其他契约对象与当前实际实现一致；
- 根据契约载体和影响风险运行相关的 schema / 接口校验、生成检查、类型或构建检查，
  以及必要的单元、集成、端到端或运行时回归；不机械要求与变更无关的全量测试；
- 纯文档契约至少完成增量映射与代码一致性复核；没有实际运行证据时，不得声称运行
  链路无异常。

若失败只来自不改变既定语义的机械合并错误，本 Skill 可以在正式契约整合边界内修正
并重新发起验证。若修正需要改变代码、已验收行为、临时契约语义或其他共享契约，
暂停受影响项并判断是否需要新增决策，不得通过连续补丁绕过已通过的里程碑。

仅在本次确需正式契约写入且权威路径/格式无法由项目约定确定时，提出具体方案确认。

## 自检

只核对当前模式适用的完成条件；引用已有证据，不因清单重复运行验证。

- [ ] PRD 和 STEP 正文未被修改或重新解释
- [ ] 里程碑数量来自实际依赖和用户约束，而非固定模板
- [ ] 每个 STEP 只属于一个里程碑，且未遗漏
- [ ] 每个里程碑可独立验收，并有明确进入条件
- [ ] 合批 STEP 满足独立、无冲突、可分别验收
- [ ] 文档路径优先复用项目约定
- [ ] 新阶段的计划、共享进度和临时契约统一位于 STEP 目录下的 `execution/`
- [ ] 两个 Skill 共用一份 `{功能名}开发执行记录.md`，没有生成第二套状态源
- [ ] 执行中只更新临时契约，全部里程碑完成后才整合正式契约
- [ ] 正式契约中的每项有效变更均可回溯到唯一临时契约和来源 STEP
- [ ] 正式契约已与受影响实现对照，并完成与风险相称的合并后回归验证
- [ ] 执行器只提交 `CONTRACT_VERIFICATION_READY`，最终契约闸门由本 Skill 判定
- [ ] 有契约增量须 `CONTRACT_MERGED_VERIFIED`；无增量须有 `NOT_APPLICABLE` 依据，且其余验收通过
- [ ] 影响范围/验收的未决问题已暂停受影响项，未擅自改写需求
- [ ] `orchestrated` 只接收 `steps-verified.md`，只生成执行计划
- [ ] 关键路径和符号没有 `UNVERIFIED`
- [ ] 总控仅规划时标记业务代码 `NOT_STARTED`；执行模式记录真实状态
- [ ] 实际编码由 `$execute-approved-work` 按 STEP 边界执行，没有建立第二套切片或完成状态
- [ ] 执行器只提交闸门证据，里程碑通过与推进仍由本 Skill 判定

# 文档缺口补齐（doc-gap-fill）

## 用户意图（原文，须遵守）

主要是用在补齐和文档遗漏的小功能用：

- 你先看下开发文档，要100%完成开发文档的内容
- 然后对比下，文档需要做的，现在已经实现的服务端情况，已经实现的UI现状
- 然后你看看怎么修复，并且要结合原来版本后台的UI规则，给我个方案，可以适当美化结构，更利于使用
- 对比现在已经实现的代码仓内容，如果有问题请向我提出问题，比如边界，冲突，模糊 等问题，给出问题选项，建议，demo，场景等
- 等确认后再开发，先确认方案

## 何时使用

仅在用户要求使用本技能，或明确要求对照开发文档查缺口并先给方案时使用；提及技能供审查不算调用。

**不替换既有流程**：已有明确范围和执行方案时复用原执行器；普通缺陷修复不重新进入本流程。

## 硬规则

1. **定向读取**：用户已指定文档或模块时，直接读取对应资料及必要实现；不先扫描整个仓库。
2. 目标文档或项目仍存在实质歧义时，先查询已知上下文；无法唯一定位再集中询问，不为已明确范围重复确认。
3. **先不改代码、不写/改项目文档**；只输出对照、方案与确认题。
4. **开发文档是完工标准**：点名文档中的要求须逐条对照，目标 100% 覆盖（未做 / 半做 / 偏离均标出）。
5. **UI 范围动态**：有后台缺口则对照既有 admin UI 规则；有 H5 缺口则对照既有 H5；纯服务端可无 UI 方案。不预设「一定改后台」。
6. 集中提出尚未解决的实质决策；只要求方案时不进入开发。已有确认方案和执行授权直接复用，不因本技能再次确认。
7. **最小范围**：不顺手改无关功能；美化仅限更利于使用的结构/信息架构，不另起视觉体系。

## 阶段 0：锁定范围（门禁）

先从请求、已确认上下文和已指定文档确定范围；仅目标来源或项目无法唯一定位时暂停相关读取并询问：

需要确定的事实（能够核实的自行确定）：

1. **开发文档**：优先用户路径或引用；只指定模块时定向查找其权威开发文档，多个来源无法判定时请用户选择。
2. **对比范围**：默认仅已指定文档中与当前任务相关的条目，遵守用户明确排除项。
3. **UI 是否纳入本次**：按文档要求和实际缺口判断；用户未单独说明 UI 不构成读取阻塞，明确排除时遵守。
4. **代码根目录**：默认当前目标项目；引用跨项目且无法核实时再询问。

简短记录已确定范围后进入阶段 1；必要问题尚待回答时继续不受影响的只读核查。

## 阶段 1：文档清单化（100% 拆条）

仅读取**已确认**的开发文档，抽出可验收条目：

| ID | 文档要求 | 类型(API/表/任务/后台/H5/其它) | 验收标准 | 来源 |

不得把未点名文档中的内容并入清单。

## 阶段 2：三方对照

在已确认范围内读代码，对每条标注：

| ID | 文档 | 服务端 | UI（若本次纳入） | 结论 | 证据路径 |

结论取值：一致 / 部分实现 / 缺失 / 偏离文档。  
本次明确「不含 UI」时，UI 列填「不适用」。

## 阶段 3：修复方案（仍不写代码）

1. **推荐改法**：步骤化，文件/函数粒度；对齐文档验收标准。
2. **UI 方案**（仅当对照显示有 UI 缺口）：
   - 先读**同项目既有**同类页面/公共样式/API 封装，沿用原规则；
   - 可适度美化结构（分组、操作路径、空态/加载），不重做设计语言；
   - 若缺口在后台，优先对齐现有 admin 模式；若在 H5，对齐现有 H5 模式。
3. **备选**（有明显权衡时给 1 条）。
4. **验证点**：关键路径 checklist（不强制写测试，除非用户要求）。

## 阶段 4：确认题（一次全部抛出）

对边界 / 冲突 / 模糊 / 文档与实现不一致处，**同一回复内列出全部阻塞确认题**。无则写“无阻塞确认项”；只授权方案时交付方案，已确认方案且实施获授权时继续。

每条格式：

```text
────────────────────────────────
【确认点 N】标题
────────────────────────────────
现象 / 冲突：…
场景：什么情况下会碰到
选项：
  ▸ A：名称
    场景：…
    做法：…
    风险：…
  ▸ B：…
Demo（可选）：请求示例 / 页面路径 / 假数据
AI 建议：选 X，因为…
────────────────────────────────
```

文末汇总：

- 推荐方案一句话
- 待用户确认的选项列表（N 个）
- 当前状态：仅方案 / 存在待决事项 / 已授权实施；不自动把每次输出都标为待确认

## 阶段 5：确认后开发

用户明确确认（或逐条选定选项）后：

- 严格按已确认范围与选项实现；
- 实施中发现需要新增范围或关键取舍：暂停受影响项并提出决定，其他独立已授权项继续；实现偏离已确认要求按正常缺陷修复；
- 不做文档外的「顺手优化」。

## 与其它技能

| 场景 | 用哪个 |
|------|--------|
| 需求【待确认】逐条拍板 | req-confirm |
| 已定改点，只要最小改动分析 | pre-change-analysis |
| 改完对照 contract 复查 | contract-change-review |
| 大模块 M1/M2/M3 | milestone-step-execution |
| **文档已写清的小功能遗漏补齐** | **本技能** |

## 输出清单（每次完整跑通须具备）

1. 范围复述（文档 + 模块 + UI 是否纳入）
2. 文档覆盖表
3. 三方对照表
4. 修复方案（含动态 UI 方案或「无 UI」）
5. 全部确认题（一次抛出）
6. 当前授权与未决事项；无新决策不重复确认

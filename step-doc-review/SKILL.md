# STEP 文档审查、修复路由与权威复审

## 手动触发

仅在用户要求使用 `$step-doc-review`，或已授权上游流程按协议交接时使用。讨论或审查本技能本身不算调用。普通谈话中提到 STEP、覆盖率、遗漏、幻觉或需求比对，不自动触发。

## 定位与边界

先用 PRD 和可验证事实全量审查，再把问题路由给唯一责任方；只有对当前候选和当前来源完成完整复审后，才签发 STEP 权威状态。

本 Skill 负责审查、分类、修复边界、完整复审和 `STEPS_VERIFIED`。它不替用户选择产品语义，不实施业务代码，不编排里程碑，也不自行完成未被唯一限定的结构重写。任何模式都不得覆盖用户原 STEP。

## 入口与模式

- `standalone`：用户直接调用；按其意图进入 `review-only` 或 `review-repair`，交付本阶段结果；后续未获授权则结束，已授权的内部交接由调用方继续。
- `review-only`：只审查和分类；用户允许报告落盘时更新 `step-audit.md`，明确只读时在回复交付。不写候选 STEP，路由结论不产生修改授权。
- `review-repair`：用户已明确授权文档修复；先完成审查和分类，再按本 Skill 的单一写入方规则修复并复审。
- `orchestrated`：在 `$prd-delivery-harness` Phase 2 内执行；复用其来源清单、产物和校验器，不新增阶段或第二状态源。结构修复只把 `$execute-approved-work` 当作调用方托管的文档执行协议。

用户已确认输入和继续意图时不重复确认。缺少 PRD、STEP 正文或判断必需来源时，直接返回相应阻断结果。

## 输入、证据与新鲜度

至少需要原始 PRD 与待审 STEP；只定向读取 STEP/PRD 引用或判断必需的代码、契约和项目规范。支持本地路径、可访问链接、PDF、Word、Markdown、纯文本和粘贴内容。

事实优先级：`USER_DECISION` → `PRD` → `CONTRACT` → `REPO_BASELINE` → 项目规范 → 派生 STEP/报告。来源标签只用 `USER_DECISION`、`PRD`、`CONTRACT`、`REPO_BASELINE`、`RUNTIME`、`PLANNED`、`UNVERIFIED`；代码事实未读取时必须标 `UNVERIFIED`。

- 首次审查和签发权威状态前，记录并核对本轮实际使用的 PRD、原 STEP、候选 STEP、必要契约和关键代码文件 SHA-256。
- `orchestrated` 复用 `source_manifest/source_digest`；`standalone` 只登记核心来源，不扫描整个仓库。摘要变化时暂停沿用旧结论，先核对差异，从最早受影响检查重做并绑定新摘要；无语义影响的部分记录复用依据。不能只改摘要字段绕过真实校验。
- 定位优先使用需求 ID、标题、STEP ID、符号或契约条款；当前行号只作辅助，不能单独作为稳定证据。
- `RUNTIME` 必须来自真实执行，至少含命令、工作目录、原执行时间、退出码、关键输出及对应代码/环境。前提未变且可核实的历史运行证据可复用，须标注“历史运行，本轮核实复用”；不能宣称本轮重跑。环境、数据、代码或依赖变化及证据不充分时重验受影响项。

## 完整审查

首次审查覆盖完整输入；签发前对最终候选和当前来源完成一次完整复审，不只看 Diff。中间机械修复轮检查改动及依赖影响；涉及语义、结构、覆盖关系或无法限定影响时扩大到完整复审。同一未变候选已完成的完整复审不再重复。九维状态只允许 `PASS | FAIL | BLOCKED | UNVERIFIED | N/A`；`N/A` 必须写理由，不使用数字总分。

| 维度 | 必查内容 |
|---|---|
| 1. 幻觉 | 无来源字段、值、状态、错误码、顺序、路径、符号、测试要求和完成声明 |
| 2. 遗漏 | 有效需求、验收、排除/禁止项、PRD 明示技术债和文档动作是否都有 STEP 处置 |
| 3. 冲突 | STEP 与用户决定、PRD、必要契约及代码基线的可测试矛盾；代码现状不能取消 PRD |
| 4. 清晰度 | 多义选择、笼统完成标志、无核实目标的“待查”、不存在引用和不可执行描述 |
| 5. 依赖 | 缺失、多余、断链、循环及隐藏依赖；异常时先判断应修依赖边还是拆分范围过宽的节点 |
| 6. 可测性 | 每个完成标志都有具体输入、行为/断言和可观察结果，不以“正常/测试通过”代替 |
| 7. 覆盖率 | 所有有效需求/决策/验收 ID 唯一映射；安全硬约束和禁止项不得漏映射 |
| 8. 技术债 | 每个 `TD-*` 直接来自 PRD 或 `USER_DECISION`；派生文档和代码缺口不能自行升级为技术债 |
| 9. 代码事实 | `existing` 路径、符号、接口、命令和结构已真实读取；来源、定位和值一致 |

以下动作并入九维，不新增维度：

- 在把问题定为产品决定、安全/权限/数据/公开接口风险或权威冲突前，主动检查能否由其他权威来源推翻当前结论；没有唯一答案时不得自修复。
- PRD 明示跨页面或跨模块关键流程时，在可测性和覆盖率中核对“入口 → 用户动作 → 客户端状态 → 请求/命令 → 服务结果 → 页面反馈 → 失败恢复”；纯后端或纯文档任务不强加 UI 链路。
- 验收要求比较“这些对象/记录/字段”时，必须在同一输入快照下比较稳定 ID 集合/多重集；无稳定 ID 时比较相关可见字段元组多重集。数量相同不等于对象一致。
- 验收只限定某类请求、系统层级或输出时，只能由直接验证该对象的 STEP 覆盖；不得从服务端 403 擅自推出按钮隐藏等未要求行为。
- 审计内只保留一个规范化覆盖视图；正向、反向和逐 STEP 展示均与其做集合差异，范围表达式展开后过滤已废止或替代 ID。
- 每项发现记录 `obligation_source` 与 `scope_class`；`REPO_BASELINE` 只能证明现状，不能单独创造 PRD 修复义务。
- STEP 依赖但尚未定位的现有入口、路由、下载约定或验证命令不能无风险通过：有明确实施前停止门时至少为 `PASS_WITH_RISKS`，影响核心可行性或验收时为 `DOCUMENT_ONLY` 或 `BLOCKED`。

## 问题契约

`step-audit.md` 中每项发现使用本轮不可变 ID，并包含七组信息：

| 字段组 | 必需内容 |
|---|---|
| `ID` | 唯一编号 |
| `证据` | 来源类型、来源摘要、稳定定位、必要的当前行号 |
| `类型与理由` | 下表类型、严重度、`obligation_source`、`scope_class` 和分类理由 |
| `目标与边界` | 预期结果、唯一目标、允许范围、禁止改变内容 |
| `责任与授权` | `repair_owner` 及当前是否已有文档修改授权 |
| `验证` | 可复核的解决判据，不能只写“已修改” |
| `状态` | 待确认、待修复、已执行待复审、复审通过、无须修改或阻断 |

## 分类与责任方

| 类型 | 判定 | 责任方与动作 |
|---|---|---|
| `PRODUCT_DECISION` | 两个及以上合理解释，或会改变业务范围、行为、验收、安全/权限语义 | 用户确认；确认前不写同一候选 |
| `DETERMINISTIC_DOC_ERROR` | 权威证据直接给出唯一答案，且修改不改变需求语义 | 有修复授权时由本 Skill 局部修复并完整复审 |
| `APPROVED_STRUCTURAL_REPAIR` | 需拆分、合并、重排 STEP 或重建依赖/映射，且审核已给出唯一目标和边界 | `$execute-approved-work` 按 finding ID 执行 |
| `SOURCE_OR_EVIDENCE_BLOCKED` | 来源冲突未解、换版影响未核实、必要代码/契约或有效运行证据缺失 | 可自行核实的先核实；需要来源 owner 或用户决定时交回 |

“文档写错”不自动等于可自修复；只要会改变语义，就不能归为 `DETERMINISTIC_DOC_ERROR`。“结构有问题”也不等于已批准修复；目标或边界不唯一时仍须阻断。

## 单一写入方与交接

每个候选修复轮只允许一个写入方：

1. 有未解决的 `PRODUCT_DECISION` 或 `SOURCE_OR_EVIDENCE_BLOCKED`：冻结受影响候选，不签发权威版；继续不受影响的只读审查。独立部分修复仅在已明确授权且能隔离的候选中执行。
2. 否则只要存在一个 `APPROVED_STRUCTURAL_REPAIR`：本轮所有已批准项（含机械项）统一交给 `$execute-approved-work`，本 Skill 不同时写该候选。
3. 全部为 `DETERMINISTIC_DOC_ERROR`：有修复授权时由本 Skill 自修复。
4. 用户明确只修部分问题时，缩小授权 ID 集并生成新的候选版本；不得让两个 Skill 交替修改同一版本。

交给 `$execute-approved-work` 时只加载其入口及“调用方托管的 STEP 文档修复”参考；同版本已读内容复用。只传：

```text
audit_path, source_digest, candidate_input_path, authorized_finding_ids,
expected_target_per_id, allowed_scope_per_id, forbidden_changes_per_id,
verification_per_id, output_candidate_path
```

执行器必须返回：`finding_id → changed_location → verification_evidence → item_status`、`candidate_sha256`、`handoff_state = STEP_REVIEW_READY`。来源摘要变化、目标不唯一、需要改变 PRD/验收/业务语义或会覆盖原文时，执行器暂停受影响项并交回。未授权相邻问题只记录，只有它阻塞授权项或产生共享影响时才暂停。

## 修复、复审与权威状态

必要交接状态只有：

```text
REPAIR_REQUIRED → STEP_REVIEW_READY → STEPS_VERIFIED
```

- `REPAIR_REQUIRED`：审查完成但输入仍需修复；`STEP_REVIEW_READY`：授权修复已执行并有证据，只表示候选可复审。
- 同轮由本 Skill 自修复且来源未变时，完整复审通过后可直接形成 `STEPS_VERIFIED`。
- 跨 Skill 修复后交回本 Skill 完成复审；已有修复和复审授权时自动继续，不要求用户重复点名。跨会话先恢复授权、候选与来源摘要，复用仍有效证据；候选或来源变化时按影响重新核验，签发前仍须覆盖当前完整候选。执行器工作项 `VERIFIED` 不等于 STEP 权威。
- 最多两轮修复；仅映射或依赖受影响时重建对应部分，结构变更时检查全局一致性。最终签发前完整复审。同一问题在证据未变时重复、修复不收敛或出现语义未决时暂停受影响修复。

## 阶段结果

| 结果 | 使用条件 |
|---|---|
| `PASS` | 完整复审通过且无风险 |
| `PASS_WITH_RISKS` | 完整复审通过，仅有明确非阻断风险 |
| `DOCUMENT_ONLY` | 可完成文档比对，但缺少判断必需的代码/契约，不能形成验证版 |
| `BLOCKED` | 需要产品决定、来源 owner 或高风险确认 |
| `FAILED_VALIDATION` | 当前 STEP 的结构、映射、依赖、验收或产物未通过 |

`review-only` 发现确定性问题时仍返回 `FAILED_VALIDATION`，并标记 `REPAIR_REQUIRED`；不能因“可修但未授权”改判 `DOCUMENT_ONLY`。只有 `PASS`/`PASS_WITH_RISKS` 且本次允许产物写入时才能生成 `steps-verified.md`；明确只读时只报告结论，不写文件。其余结果不得签发权威版。

## 产物与命名

本 Skill 生成的 Markdown 文件名去掉 `.md` 后，必须与第一个 H1 文本完全相同：

- `step-audit.md` → `# step-audit`
- `steps-candidate-rN.md` → `# steps-candidate-rN`
- `steps-verified.md` → `# steps-verified`

`step-audit.md` 是唯一当前审计记录，内部保留首次发现、用户决定引用、修复映射、逐项 Diff、完整复审、风险和阻断；不默认另建初审报告或当前补充报告。跨 Skill/跨会话修复生成 `steps-candidate-rN.md`；同轮内存候选直接通过时，不强制保留与验证版重复的候选文件。原 STEP 始终只读。

## 自检

- [ ] 九维审查及最终候选完整复审有状态与证据；未变候选不重复复审
- [ ] 每项发现满足七组问题契约并正确路由
- [ ] 高风险分类已做反证检查，关键流程按条件检查
- [ ] 当前来源摘要匹配，变化影响已核验；定位不只依赖行号
- [ ] 当前修复轮只有一个写入方，且未覆盖原 STEP
- [ ] 执行器结果只到 `STEP_REVIEW_READY`
- [ ] 只有完整复审通过才生成 `steps-verified.md`
- [ ] 所有生成 Markdown 的 basename 与第一个 H1 一致
- [ ] 已返回五种结果之一；已授权交接继续，无授权后续则结束

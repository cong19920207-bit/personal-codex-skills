# 改代码前先分析与定方案

## 何时使用

用户明确要求先分析后决定实施，或实际发现尚未决定的范围、产品语义或重大跨模块取舍时，使用本技能。普通修复和已确认方案的实施不增加审批；需要的根因分析可直接在执行流程内完成。沉默不等于授权。

已有明确实施授权且没有新增实质取舍时，简短说明必要分析后继续，不要求用户补说“直接改”。用户只要求分析或明确先不修改时，保持只读。

## 分析流程

1. 明确本次是只读分析还是已授权实施；定向读取相关代码和证据，诊断不得越过数据与外部操作授权。
2. 按问题规模给出原因、影响及证据；下文小节按需合并，无实质影响的维度省略。缺失且无法自行核实的决策信息才列为待确认。
3. 输出 **「修改方案」**（最小范围、对齐原始需求）。
4. 只读分析交付结论；已授权实施且无新增决策则继续。只有执行未获授权或方案引入实质新取舍时，集中提出具体确认点。

## 分析说明（输出结构）

按需覆盖以下内容，可合并为简短说明，不强制每次逐标题输出。

### 1. 原因

- **技术原因**：缺陷或缺口在代码/数据/配置/环境中的直接成因（因果链一两步即可，避免空泛）。
- **需求/业务原因**（若适用）：与产品规则、边界条件、历史决策的关系。

### 2. 场景

- **复现或触发条件**：输入、时序、环境、用户路径等。
- **是否稳定复现**：每次 / 偶发 / 仅特定数据；若无复现路径，写明依据（日志、报告、静态分析等）。

### 3. 影响范围

- **功能面**：哪些功能、页面、API、任务会受影响。
- **代码面**：拟动文件/模块/依赖方向；是否涉及公共组件、契约、数据库、缓存、消息。
- **用户/数据面**：是否需要迁移、兼容旧客户端、回滚策略要点。

### 4. 必要性

- **不修的后果**：安全、正确性、可用性、合规、可维护性中的哪类会受损。
- **是否必须现在修**：必须 / 建议 / 可选；若可选，说明接受条件或后续触发条件。

### 5. 风险等级

使用 **高 / 中 / 低** 三档，并各用一句话写清**主要风险来源**（例如：破坏兼容、并发、数据迁移、隐蔽依赖）。

| 等级 | 典型含义 |
|------|----------|
| 高 | 易导致生产事故、数据错误、大范围回归或难以回滚 |
| 中 | 局部回归、需重点测某条链路或需协调发布 |
| 低 | 隔离良好、行为可预测、回滚简单 |

## 修改方案（输出结构）

### 原则

- **最小范围**：只动满足原始需求所必需的代码与配置；不做顺手重构、不扩大需求。
- **原始需求不变**：不擅自改产品语义；实现偏离明确需求时按需求修复；只有权威要求间存在无法消解的冲突或需改变产品语义时交用户决策。
- **不影响其他功能**：标明将**避免**触碰的模块与将做的**隔离措施**（如仅在分支内处理、加守卫条件、保持 API 不变等）。

### 方案内容建议包含

1. **推荐改法**：步骤化（1→2→3），每步对应文件/函数粒度（不必到行号，除非已读过代码）。
2. **备选改法**（可选）：仅在存在明显权衡时给一条更保守或更彻底的选项，并说明取舍。
3. **验证方式**：应测的关键路径或检查点（不强制写测试脚本，除非用户要求）。
4. **回滚要点**：若失败如何恢复（配置开关、单次提交可回滚等）。

## 与「直接开改」的衔接

用户确认方案后：

- 严格按已列**最小范围**实施；若实施中发现前提不成立，核实影响；超出已授权范围或改变关键取舍时暂停受影响部分并请求决定，独立已授权工作继续。
- 用户规则中若要求中文注释、保留既有逻辑等，在编码阶段一并遵守。
